# Lex 4.4.3

This patch corrects destination provenance for trusted scope-bound Frame stores. It does not change stored Frame schemas or tenant/workspace enforcement and needs no database migration.

An injected PostgreSQL Pool without verified host evidence now reports an explicit unknown backend plus a per-instance diagnostic reference. The old placeholder-derived identity was identical for unrelated injected Pools using the same schema and must not be used as destination proof. Trusted hosts can explicitly supply a secret-free verified backend fingerprint; the selected schema also participates in the destination identity.

The new `lex destination --json` command and fifteenth canonical MCP tool, `destination_inspect`, return an authorized workspace destination snapshot without reading Frame history, probing store health, or writing Frames. They request the intended `remember` / `frame_create` capabilities. Optional `--expected-destination` and `expected_destination` restrictions reject a mismatched or unverified destination before writes, and CLI/MCP save receipts report the same destination shape. The restriction grants no authority or persistent consent.

Destination identity binds backend, schema, roots, binding, tenant/workspace, repository, principal, capabilities and authority revisions. MCP checks before cached success and isolates idempotency responses by destination. Canonical authority resolves at operation entry; backend evidence is host-supplied at its recorded `verifiedAt` and a long-lived host may retain it. Expiry and expected binding are checked again before save. This is not transaction-coupled backend or revocation revalidation. Read the [destination contract](../DESTINATION_PROVENANCE.md) before treating a receipt as evidence.

Destination consumers need no API migration. Compatibility hosts can keep their existing workflow but cannot supply trusted workspace destination proof. `remember --dry-run` remains read-only and cannot be combined with expected write-destination binding. Module scope, frame permissions, caller provenance and environment variables never supply this verification.

Publish the exact Lex 4.4.3 artifact first, then its matching Lex-MCP 4.4.3 wrapper, before signed release tags and Registry publication. Retain the existing qualified 4.4.2 package pair and installed-runtime lock for recovery. Package publication does not install or activate a new scoped runtime; host/AXF deployment and actual consumer qualification remain separate. See the [4.4 migration and recovery guide](lex-4.4-migration.md).

The regression suite covers two backend fingerprints, unknown Pools, separate schemas/workspaces, real CLI/MCP capability alignment, zero Frame access in preflight, receipt parity, binding drift, payload spoofing, idempotency boundaries and request-local cleanup. Native Windows packed-consumer and protected publication receipts must qualify the exact release artifact. This document describes the candidate and is not evidence that publication or runtime activation occurred.

## Bundled native driver and install surface

This candidate also pins `better-sqlite3-multiple-ciphers` to 13.0.3, replaces the full Inquirer umbrella with exact `@inquirer/input` 5.1.2 and `@inquirer/confirm` 6.1.1, and removes Lex's informational postinstall hook. SQLite 13 bundles Node-API binaries and has no install lifecycle hook; consumers do not need a compiler, rebuild, or binary download. Other dependencies, including Sharp and development tooling, may still have lifecycle scripts. This does not claim a script-free dependency graph.

Node remains >=24. The upstream native platform boundary changes: Linux glibc now requires >=2.35, and Windows x86/Linux armv7 are no longer available. Bundled targets are Windows/macOS x64 and arm64, and Linux glibc/musl x64 and arm64. Release qualification exercises Linux x64 and Windows x64; other bundled targets are not independently qualified by this release. See [native support and recovery](../dev/sqlite-bindings.md).

There is no Lex schema, cipher or key-derivation migration. Synthetic plaintext and SQLCipher schema-14 fixtures generated by the actual previous locked driver 12.11.1 are read without changing original bytes or sidecars, then disposable copies are written and reopened. An explicit retained-old-binary qualification also checks old-reader reopen after new writes and the reverse direction. This is compatibility evidence for those fixtures on the tested platform, not proof for every historical store. Preserve existing backups and investigate failed integrity/key checks before changing a selected store.

The driver's exports map hides its bundled declarations under strict NodeNext. A normal production `@types/better-sqlite3-multiple-ciphers` npm alias to `@types/better-sqlite3@9.6.0` supplies the common API, and exported `CipherDatabase` preserves the previously exposed `key`/`rekey` methods on Lex-created and supplied cipher handles. Runtime resolution remains the cipher package. The supplied-handle type assertion retains the old cipher-handle invariant; it does not add cipher methods to arbitrary external drivers. Clean packed consumers check these public methods with strict NodeNext and no `skipLibCheck`.

A seventh mandatory candidate gate now installs and exercises the exact tarball with `--ignore-scripts`, in addition to normal lifecycle installs. Both paths verify that the exact bundled platform `.node` loaded, FTS5 works, public exports/declarations resolve, image rendering works, and the published example returns its receipt. Protected Windows smoke runs both modes with explicit exit guards. Package integrity and bundled binary inventory are verified; upstream native build provenance is not independently attested by this work. Publication and installed-runtime activation remain separate steps.
