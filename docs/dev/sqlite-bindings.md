# SQLite Native Bindings

Lex 4.4.3 pins [`better-sqlite3-multiple-ciphers` 13.0.3](https://github.com/m4heshd/better-sqlite3-multiple-ciphers/releases/tag/v13.0.3).
The published dependency contains Node-API binaries and has no `preinstall`, `install`, or
`postinstall` hook. Lex also has no installation hint hook. Normal installs and installs with
lifecycle scripts disabled must load the bundled binary without downloading or compiling a
replacement.

## Supported environments

Lex requires Node.js 24 or newer. See `.nvmrc` for the pinned contributor/test version.
The dependency includes these platform binaries:

| Operating system / C library | Architectures |
| --- | --- |
| Windows | x64, arm64 |
| macOS | x64, arm64 |
| Linux / glibc 2.35 or newer | x64, arm64 |
| Linux / musl | x64, arm64 |

This is the upstream binary inventory, not a claim that Lex has qualified every combination.
Release evidence identifies the actual tested platforms. Windows x86 and ARMv7 are outside this
inventory. Node-API avoids the old per-Node-version ABI rebuild requirement, but operating-system,
architecture, C library and native-loader compatibility still matter.

Install dependencies separately on Windows and WSL. Do not copy `node_modules` across platforms.
An unsupported platform or failed binary must produce a failed check; Lex's qualification flow
does not silently compile or download another native module.

## Verify the installed dependency

From a contributor checkout:

```bash
npm ci --ignore-scripts
npm run check-sqlite
```

The check loads the native module, exercises FTS5 in memory, and creates a disposable encrypted
SQLCipher database. It verifies that an unkeyed reader fails, then reopens the database with the
synthetic key and checks its contents and integrity. Temporary databases are removed afterward;
the check does not read or repair a user's store.

`npm run rebuild-sqlite` remains a compatibility alias for this health check. It no longer
rebuilds anything. Normal installation does not require a C++ toolchain or a native rebuild step.

## Release qualification

CI checks the bundled native module after installing the locked graph with lifecycle scripts
disabled. Packed-consumer gates exercise both normal installation and `--ignore-scripts`
installation, including the Windows candidate lane. Compatibility tests use synthetic plaintext
and SQLCipher fixtures generated by the previous locked driver, 12.11.1; original fixture bytes
are preserved, and write/reopen checks use disposable copies.

These checks establish behavior for the tested candidate and environments. They do not establish
independent provenance for upstream native binaries or promise that every dependency in the full
development graph has no lifecycle scripts.

The `scripts/ci.sh` script checks SQLite before running tests. Pass `--pretty` (or its exact
`--prettier` alias) through `npm run local-ci --` to add the repository-wide, check-only formatting
audit. It never invokes `prettier --write` or `npm run format`.

## Troubleshooting

If the bundled module fails to load:

1. Check the actual Node version, operating system, architecture and Linux C library against the
   supported environment above.
2. Confirm the selected package is the exact locked/published dependency; reinstall the verified
   package in the same environment if its files are missing or corrupt.
3. Run `npm run check-sqlite` in the checkout and retain its failure output and package identity.
   Do not add an automatic source-build fallback to turn the gate green.

If the health check passes but a selected store fails, confirm its credential-free identity first.
Establish a recoverable backup before any repair, reproduce against a disposable copy, and inspect
schema, permissions, disk space and concurrent writers. Preserve live stores and credentials;
installation and a failed health check do not authorize deleting or recreating a database.
